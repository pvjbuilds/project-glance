## Recovery design — independent preflight required

A number incremented above a backup cannot protect against a previously consumed revision hidden by a corrupt or missing primary. Introduce envelope schema 2, retaining per-project numeric versions for display but requiring an opaque compare-and-swap token composed of an envelope generation UUID and the numeric project revision on every update. The generation changes on every explicit recovery, including recovery from another schema-2 backup; random UUID uniqueness is probabilistic, not a proof against collision. An update must compare the entire token under the existing exclusive lock. A recovered schema-2 envelope never accepts legacy numeric-only updates. Old binaries reject schema 2 at their existing strict schema check, including connect/enroll; they cannot silently bypass the new guard. New updater can continue schema-1 numeric updates until explicit migration; normal migration of a healthy store creates a new generation under lock and converts the entire envelope to schema 2, so pre-migration commands fail. `list` returns the epoch and versions, and guide examples instruct users to copy the token from the read result, not construct or reuse it. Every mutating operation that accepts prior state must preserve the generation; connect also increments version while holding the lock, and cannot reintroduce schema 1.

Explicit `recover` is a separate operator action, never triggered automatically. It requires a valid backup and explicit expected backup digest plus the observed primary state (digest if present, a missing sentinel otherwise); verify both again under lock. Reject changed input, absent/invalid backup, a healthy primary by default, and mismatched acknowledgement. Before replacement, write a uniquely named protected archive containing exact corrupt primary bytes when present and retain the original backup; sync archive and directory, fail closed if preservation fails. Convert the validated backup to schema 2 with a fresh generation and durably replace primary without overwriting the backup with corrupt bytes. Report selected snapshot, archive location, fresh generation, and that later changes after the snapshot may be lost. After any post-rename error say outcome uncertain and require readback. Do not silently delete or automatically retry. With no valid backup, fail with preservation instructions; no invented reconstruction. There is no guarantee against disk rollback of *all* state, hostile local processes, UUID collision or actual power loss. Recovery is a data-loss decision: its exact snapshot and risk must be reviewable and explicitly requested before running on live data. Ordinary automated tests operate only on isolated fixtures.

Behavioral test: use real CLI to save version N and retain token, save N+1, fault the primary, recover the backup, then try the old N token and legacy numeric-only N against the restored numeric N. Both must fail, regardless of matching numeric part; a freshly read token must succeed. Additional slices cover migration and old binary rejection, backup/primary digest races, corrupted backup and archive failure, retry after uncertain rename, and concurrent callers. Need review of crash boundaries and epoch compatibility before any recovery code.
